# Vively dashboard — safety and data-loss audit
**19 October 2026 · code as of commit `a048234` plus uncommitted booking work**

Scope: authentication and access control, data leakage of creator PII, and the reported
"partner links get lost / automatically deleted" bug. Read-only audit — no code was changed.
Every line reference below was verified in `index.html`, `server.js` or `server/*.js`.

---

## The short answer

Route-level authorization is sound: all 30 routes in `server.js` and all 20 in
`server/booking-routes.js` that touch workspace data are wrapped in `requireStaff`, with no
gaps. Tokens are all CSPRNG and not guessable. Server logs leak nothing. Password storage is
pbkdf2-sha512 at 100k rounds with per-user salts and timing-safe comparison.

The real problems are four: **the save model loses other people's work**, **one backup button
writes creator bank numbers in the clear**, **the whole workspace stays on every browser's disk
after logout**, and **sign-in has no rate limit at all**.

---

## P0 — Fix this week

### 1. The partner-link bug: a stale tab silently overwrites everyone else's work
**`index.html:1749`** (and the same line in `src/model/db.js:454`)

The workspace is one Mongo document that every client rewrites whole
(`server.js:793` — `$set: { db, settings, … }`). The only concurrency control is an optimistic
revision check (`server.js:764`), and the client defeats it: when the server refuses a save
with 409, the client adopts the server's **new revision number without loading the server's
data**. The stale tab is now "up to date" as far as the lock is concerned, and its next
autosave — fired automatically by `render() → persist() → scheduleServerSave()`
(`index.html:16026`, `1542`, `1780`), with no human involved — passes the check and writes its
stale copy over the whole document.

How your symptom happens, with nothing unusual required:

1. Person A has the dashboard open since 09:00. Server revision 50.
2. Person B creates a partner link for a venue. Server revision 51. B copies the URL and sends
   it. It works.
3. A clicks any tab. Autosave fires 2 s later with revision 50 → **409**. A sees one yellow
   toast that is easy to ignore; A's copy still has the old 3 links.
4. A clicks another tab. Autosave fires with revision 51 → **accepted**. A's `partnerLinks`
   (3 entries) replaces the stored 4.
5. The venue's link now 404s with *"This link is not valid, or has been turned off"*
   (`server.js:1181`) — which reads exactly like "automatically deleted".
6. Both people see a green **Saved** badge. Nobody is told anything was lost.

Nothing expires or deletes partner links — I checked for TTL indexes, prune and cleanup code
across the tree. They can only be overwritten. The server-side guard that exists
(`server/workspace-guard.js`) refuses **only** a payload where campaigns, creators *and*
participants are all zero, and it deliberately ignores `partnerLinks`, `appointments` and
`socialContent` (`workspace-guard.js:33,47`). It never looks at `settings` at all.

**Smallest fix (one line):** delete the revision adoption at `index.html:1749` and
`src/model/db.js:454`. The stale tab then keeps getting refused until the person reloads or
explicitly clicks Save and confirms the overwrite — the existing `confirm()` at
`index.html:16223` regains its meaning.

**Proper fix, in order of value:** (a) on 409, re-read the server copy instead of just taking
its number — `serverLoad()` already exists, and the planner Refresh button at
`index.html:6456` already gets this ordering right; (b) reconcile independently-written
collections server-side instead of trusting the payload — exactly the pattern already proven
for bookings at `server.js:778` / `applyBookingSlots`; partner links are append-and-revoke-only,
so a union by token makes this symptom structurally impossible; (c) move partner links into
their own collection, as partner *comments* already were, for the reason written at
`server.js:1197`: *"writing a partner's comment into [the workspace] would collide with whoever
has the dashboard open."* That argument applies verbatim to the links.

Same root cause, also losing data today:
- **`SETTINGS.holidays` is destroyed on the first save after any page load** —
  `index.html:1659` restores only `hideBlocked` from the server, then the next save POSTs
  `settings` without the holidays. This needs no second user. Two-line fix on the load side.
- `appointments` and `socialContent` — identically unguarded.
- `restoreBackup()` (`index.html:10666`) and `sheetPull()` (`index.html:8996`) replace `DB` and
  never reset `SERVER.revision`, so the next autosave pushes the older contents server-wide.
- The `beforeunload` beacon force-saves (`index.html:1797`, `force: true`) and its freshness
  gate accepts `localLoadedOk`, which only means "localStorage wasn't empty"
  (`index.html:1795`). A tab whose load failed force-writes a days-old snapshot on close.

### 2. "Create link" tells you it worked when it didn't
**`index.html:11182`**

`serverSave({ silent: true }).then(() => toast('Link created — …'))` — the `.then` runs on a
409 exactly as on success. If B's own create is the save that gets refused, B is told the link
was created, copies it, and sends a token the server never stored. `toastAfterSave()`
(`index.html:1606`) exists for this and is used everywhere else. Revoke has the mirror problem
(`index.html:11197`).

### 3. Settings → "Download backup (JSON)" writes bank account numbers in the clear
**`index.html:10201`** (and `src/views/settings.js:106`)

`JSON.stringify({ db: DB, settings: SETTINGS })` — raw `DB`. The file contains every creator's
`payout.bank`, `payout.name` and **full account number**, plus emails, Kakao IDs/phones, postal
addresses, internal notes and blacklist reasons. `stripPayout()` already exists
(`index.html:3670`) and the campaign-delete backup uses it, with the right reasoning in its
comment: *"a file in someone's Downloads folder is the widest exposure there is."* **Both
buttons write the same filename**, `vively-workspace-<date>.json`, so afterwards you cannot
tell a safe backup from an unsafe one. One-line fix: wrap in `stripPayout(DB)`.

### 4. Sign-in has no rate limit, no lockout and no logging of failures
**`server.js:1390`** — `grep -c "rateLimit\|limited(" server.js` returns **0**.

Staff emails are not secret. Unlimited password guessing against three accounts, with nothing
in the logs to notice it by, and a success hands over `GET /api/workspace` — the whole
document, bank details included. Separately, `hashPassword` uses **synchronous** pbkdf2 at 100k
rounds on the event loop (`server.js:538`), so a few hundred concurrent login attempts peg the
single CPU and take the dashboard, the partner pages and the creator booking pages down. Both
are cheap to exploit. The rate limiter you need is already written and exported in
`server/booking-routes.js:41`.

### 5. The whole workspace — bank details included — stays on every browser after logout
**`index.html:1529`** writes `dbPayload()` (verified: `creators: DB.creators`, unmodified, so
`payout` is included) to `localStorage['vively-workspace-v1']` after every change.
**`signOut()` at `index.html:16478` never calls `clearPersisted()`** — verified line by line.
The lock is CSS-only (`body.auth-locked .app { display: none }`, `index.html:358`), and
`loadPersisted()` runs at boot *before* the auth decision, so the full dashboard is built behind
`display:none`. Reading it back needs no password — one devtools toggle, or just read the
localStorage key. `vively-sync-v1` sits beside it holding the Apps Script shared secret in
plaintext.

Any laptop a staff member used — borrowed, shared, resold, stolen, or in a remote support
session — is a copy of your creator bank ledger. Fix: keep `payout` out of the browser copy
(the server already has it) and clear the key on logout. Ideally both.

## P1 — Fix this month

### 6. The partner page sends creators' email addresses, gender and nationality
**`server.js:1143, 1145, 1146, 1150`** → rendered as columns at **`partner.html:266-270`**

The partner payload is otherwise a proper server-side projection, correctly scoped to that
partner's campaigns, and it withholds payout, internal notes, fees, addresses, Kakao IDs and
drop reasons by design. But every restaurant contact holding a link gets each approved
creator's **real email address**, gender, nationality and follower count. Nothing in the booking
flow needs them, and the staff UI's own "What a partner never sees" list (`index.html:11144`)
doesn't mention email — so nobody on the team knows it goes out. Delete the four lines; four
columns disappear from the partner table and nothing else breaks.

### 7. Internal staff notes get pasted to the venue over KakaoTalk
**`index.html:6154`** / `src/views/planner.js:226` — `(r.p.remark || r.p.note || '')`

The day sheet is explicitly the text you send the venue. `remark` is the partner-facing field;
`note` is labelled *"Internal note — not shown to the partner"* (`index.html:3756`). Whenever
`remark` is blank it falls through to `note`, so "flaky, showed up late last time" goes to the
restaurant. One-word fix: drop the `|| r.p.note`.

### 8. "Full campaign JSON", built to hand to a brand, carries addresses and phone numbers
**`index.html:5131-5139`** / `src/views/report.js:131`

`{...p, creator}` with only `payout` destructured out. The participant still carries
`fullName`, `address`, `contact` (Kakao/phone), `note` (internal) and `dropReason`; the creator
still carries `email`, `contact`, `address`, `notes`, `flag` and `flagReason`. The comment says
this hand-off "goes to a brand or a partner". Whitelist the fields instead of spreading `{...p}`.

### 9. `express.static(__dirname)` serves the entire application tree
**`server.js:669`** — confirmed live: `/server.js`, `/server/auth.js`, `/package.json`,
`/package-lock.json`, `/ARCHITECTURE.md`, `/src/**`, `/tools/**` are all public URLs. No secrets
are hardcoded (I grepped for key patterns and `mongodb+srv://` — clean), and `.env` is not
served, so this is recon rather than disclosure today. The sharp edge: `USERS_FILE` is
`__dirname/data/users.json` (`server.js:12`), and the file-based user store is the fallback
whenever `MONGODB_URI` is unset or typo'd — at which point `GET /data/users.json` serves every
account's email and password hash to the internet. Also, any CSV or backup a staffer drops in
the repo root becomes a public URL at its filename. Fix: serve an explicit `public/` directory
and move `data/` outside `__dirname`.

### 10. Google Calendar events carry phone/Kakao ID and the internal note
**`src/sync/gcal.js:145-146`** / `index.html:11350-11352` — each visit event's description
includes `Name:`, `Contact:` (the Kakao ID or phone) and `Note:` (the internal note), forwarded
verbatim by `POST /api/calendar/event` (`server.js:935`). Visible to everyone that calendar is
shared with, surfacing in mobile notifications, and retained by Google independently of Mongo.

### 11. Unauthenticated public routes with no rate limit
- `GET /api/partner/:token` and `POST /api/partner/:token/comment` (`server.js:1177, 1200`) —
  no limit and no body cap. Each GET loads the whole ~862 KB workspace document to resolve the
  token (`server.js:1071`), making a leaked link the cheapest way to run up your Atlas bill. The
  comment `author` is taken straight from the request body (`server.js:1204`) with no tie to the
  token, so a comment can be signed as anyone — and those comments are shown to staff.
- `POST /api/webhooks/instagram` (`server.js:1514`) — the signature check itself is correct
  (raw bytes, strict header, `timingSafeEqual`, fails closed with no secret, replay-deduped).
  But the **rejection** path inserts a diagnostic row keyed by the body hash
  (`server.js:1557`), so varying one byte gives unlimited anonymous inserts into
  `instagram_events`. It cannot touch workspace data.
- Booking limiter bypass: `ipOf` takes the **first** `X-Forwarded-For` entry
  (`booking-routes.js:59`), which the client controls — your own harness rotates it
  (`tools/staff-edits-page.mjs:59`). Set `app.set('trust proxy', 1)` and use `req.ip`. The token
  is also part of the limiter key, so the limiter structurally cannot limit token guessing
  (harmless in practice at 192 bits, but the control doesn't do what it looks like).

## P2 — Worth doing, not urgent

- **No security headers at all** — no CSP, HSTS, `X-Frame-Options`, `Referrer-Policy` or
  `X-Content-Type-Options`; `helmet` isn't a dependency. The dashboard can be framed by any site.
- **CSRF rests entirely on `SameSite=Lax`** plus the absence of CORS headers. That holds today
  (every mutation is JSON, no state-changing GETs), but it depends on `onrender.com` being on the
  Public Suffix List. An `Origin` allowlist on mutating routes is ~10 lines and removes the
  dependency. If you move to a custom domain, check nothing untrusted shares a sibling subdomain.
- **Sessions last 14 days with no idle timeout** (`server/auth.js:39`); `lastSeenAt` is written
  once and never updated, so there's no inactivity expiry and no "sign out everywhere".
- **Diagnostic key accepted in the query string** (`server.js:1665, 1842`) → ends up in Render's
  request logs and browser history. Header only.
- **`SIGNUP_CODE` compared with `!==` and not rate limited** (`server.js:1317`). Contained — an
  account is not authorization, since `requireStaff` checks `STAFF_EMAILS` from the environment —
  but it allows account spam and email-existence probing.
- **Slot `note` is labelled "Note (staff only)"** (`index.html:13942`) but is sent to every
  creator on the booking page (`booking-routes.js:192` → `book.html:241`). Relabel it or stop
  sending it.
- **Creator directory CSV includes `flag_reason`** free text beside a real name and email
  (`index.html:5306`) — a defamation-shaped sentence in a file that circulates.
- **Booking links CSV** (`index.html:15032`) puts per-creator invite tokens — working
  credentials — into the spreadsheet the intern works from.
- **Notion diagnostic clipboard text**, meant to be sent to an outsider, embeds a real address
  and phone/Kakao ID from the first non-empty row (`index.html:8159`).
- **`notifyStatus()` is called at `index.html:1710` but never defined there** (it exists only in
  `src/model/db.js:567`), so the client-side empty-workspace refusal throws a `ReferenceError`
  instead of returning its message. The POST still doesn't happen, so no data is lost.
- **Social content CSV has swapped arguments** (`index.html:4312`) — the whole CSV body is
  passed as the filename. Broken, not leaky.
- **`SETTINGS` is `$set` verbatim** (`server.js:793`); merging known keys would fix the holiday
  loss from the server side too.
- **Google Sheet sync** is the widest standing copy of the PII after Mongo: emails, Kakao
  IDs/phones, addresses, internal notes and blacklist reasons, behind an Apps Script deployed as
  "Anyone" and authenticated by a shared phrase in plaintext localStorage. `payout` is correctly
  excluded — the one place the `stripPayout` promise holds.

## Verified clean — don't "fix" these

- Every workspace route is behind `requireStaff`; no gaps, no ordering bypass (it's a per-handler
  wrapper, not middleware). 401 confirmed live on `/api/workspace`, `/api/workspace/meta`,
  `/api/me`, `/api/partner-comments`, `/api/booking/campaign/:id`, `/api/notion/query`,
  `/api/sheet-metrics/tabs`.
- **No env var silently disables auth.** Every one fails closed: empty `STAFF_EMAILS` → nobody is
  staff; empty `SIGNUP_CODE` → signup closed; empty `DIAGNOSTIC_KEY` → probe 404s; empty
  `META_APP_SECRET` → webhook 503s.
- **No PII in server logs.** I read every `console.*` in `server.js` and `server/*.js`: counts,
  verdicts and 12-char id prefixes only. The Instagram access token is redacted before anything
  is printed. Keep it this way.
- **The creator booking page leaks nothing about other creators** — `publicView()` returns dates,
  times and spots-left only, on the public token, the invite token, the manage link, and all four
  409 "refreshed grid" responses.
- **The partner payload is a real projection**, correctly scoped, withholding rejected and dropped
  rows, with contested campaign ids dropped from both partners.
- **No SSRF** in the sheet proxy (host hardcoded, sheet id regex-validated, gid digits only) or
  the Instagram collab probe (absolute base URL fixes the host; the local-override env var is
  ignored in production).
- **Instagram webhook signature verification is correct** — see the rejection-path note above for
  the one thing that isn't.
- **All tokens are CSPRNG and non-enumerable**: sessions 32 bytes, partner tokens 24 bytes,
  booking/invite/manage tokens 24 bytes. The only `Math.random()` in non-test code is a display-id
  fallback.
- **Password storage is sound**; cookie flags are right (`HttpOnly`, `SameSite=Lax`, `Secure` from
  `x-forwarded-proto`); a fresh session is minted per login, so no fixation; logout destroys the
  server-side record.
- **No XSS found** in the partner → staff path; `esc()` escapes all five dangerous characters and
  is applied to the partner-supplied author and text everywhere I traced.
- **`confirmedVisitAt` / `bookingId` are reconciled server-side** from the booking store
  (`server.js:778`), which is why they are the one part of the document a stale tab cannot
  corrupt. That is the shape the rest of the fix should take.

## Suggested order

1. `index.html:1749` — stop adopting the server's revision on 409. One line; stops the partner
   links vanishing.
2. `index.html:10201` — `stripPayout(DB)` in the backup export. One line; stops bank numbers
   leaving in a file.
3. Rate limit, lock out and log `POST /api/login`; make pbkdf2 async.
4. Clear `localStorage` on logout, and keep `payout` out of the browser copy.
5. `index.html:1659` — restore all of `settings` on load, so holidays stop disappearing.
6. Delete the four partner-payload fields; drop `|| r.p.note` from the day sheet.
7. `express.static` → a `public/` directory; move `data/` out of `__dirname`.
8. Rate limit the partner and webhook routes; derive the comment author from the token.
9. `helmet` + an `Origin` check; header-only diagnostic key.

A note on the pattern worth keeping in mind: in several places the code's **comments** describe
the intended policy more accurately than the code implements it. `index.html:3654` says
`stripPayout` guards four exits — it guards one. `index.html:11144` lists what a partner never
sees — email isn't on the list and isn't withheld. `index.html:3756` labels `note` as not shown
to the partner — two paths show it. Each is a one-to-three-line fix, and in each case someone
already knew the rule and wrote it down.
